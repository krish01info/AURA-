## Android stack
- **Language:** Kotlin 2.0.21 only, no Java sources. JDK 17.
- **UI:** Jetpack Compose with Material 3 and Navigation Compose (routes in `ui/AURAApp.kt`). One `MainActivity`,
  which must stay a `FragmentActivity` so BiometricPrompt works. The assistant popup and bubble are overlay windows.
- **Architecture:** MVVM. Screen -> ViewModel (`StateFlow`) -> singletons in `agent/`, `skills/`, `policy/` ->
  Room DAOs, Retrofit clients, Supabase.
- **DI:** Hilt, including `hilt-work` for WorkManager workers (`@HiltWorker` + `@AssistedInject`).
- **Async:** Kotlin Coroutines & Flow.
- **Networking / Storage:** Retrofit + OkHttp + kotlinx.serialization (Groq, Gemini), Supabase via Ktor (Postgrest,
  Auth, Realtime), Room (DB v7 with AutoMigrations), DataStore, EncryptedSharedPreferences, WorkManager.
- **Other:** Accessibility service, Android SpeechRecognizer and TextToSpeech, Vosk offline keyword spotting
  (native code, ARM only), AndroidX Biometric.
- **SDK:** `minSdk` 29, `targetSdk` and `compileSdk` 35. AGP 8.7.3, Gradle wrapper 9.2.0.

## Folders and modules
- One Gradle module, `android/app`. Run Gradle from `android/`.
- `android/app/src/main/java/com/aura/`: one package per area (`agent/`, `skills/`, `policy/`, `voice/`, `ui/`, ...).
  Each package has a `package.md`; update it in the same change when you add, rename or delete a class.
  Don't reorganize packages unless asked.
- `android/app/src/main/assets/app_shortcuts.json`: built-in skills as data. Phones download it from `main` every
  day, so a merge reaches every phone without an app update.
- `android/app/src/main/res/`: strings, themes and XML configs (accessibility service, backup rules, file provider).
- `android/app/src/test/`: JVM unit tests (fast, run on every change). There are no `androidTest/` tests yet.
- `android/app/schemas/`: Room schemas generated by the build. Commit new ones; never edit them by hand.
- `docs/`: plans, design and research. `.github/workflows/`: CI (`android-ci.yml`) and releases (`release.yml`).
- `.claude/skills/code/`: the code skill (`/code` in Claude Code) with its checklist and examples. In this repo
  it lives here, not in `agents/skills/code/` as `repo_rules.md` §7 says.
- Don't edit `agents/` rules, the code skill or Gradle wrapper files without asking.

## Android code in this repo
This adds to the code skill. Where they differ, this section wins. The skill's Fragment, ViewBinding and XML
layout parts don't apply: screens are Compose, and the assistant popup is plain Views built in code.

**Safety path.** These decide what runs without asking:
- `policy/PolicyEngine` gives each step its risk. Risk is never hard-coded anywhere else, including the UI.
- `agent/TaskManager.runStepsInternal` is the approval gate: user rules, the Send/Pay tap check, unrequested calls.
- Approval: `ui/viewmodel/HomeViewModel` and `voice/WakeWordService.askApproval`. A spoken or tapped yes may
  approve HIGH steps only; CRITICAL steps need `policy/BiometricGate` inside AURA's own screen.
- `agent/ActionExecutor.isAllowedIntent` is the intent allow-list. `skills/CloudSkillVetting` checks downloaded
  skills. `agent/LiveTaskRunner` checks a live task's word steps before listening starts.
- `policy/PromptInjectionDefender` and the `[UI_CONTENT_START]` fence in `llm/PlannerPrompt` keep screen text
  from acting as instructions.
- Never lower a risk or widen an allow-list as a side effect. A change here gets its own commit that says what
  can now run without asking, plus a unit test.
- AURA never types passwords, PINs or OTPs and never works an app's lock screen; it waits for the user.

**Services and overlays.**
- `accessibility/AURAAccessibilityService` binds `ActionExecutor`. Any step that touches the screen must cope
  with the service being off (`ActionExecutor.isBound`).
- All listening goes through `voice/WakeWordService`: one `SpeechRecognizer` at a time. Its microphone
  foreground service may only start while AURA is in front (Android 14+), never from boot.
- Overlay windows: `voice/AssistantOverlay` tries `TYPE_ACCESSIBILITY_OVERLAY` first, then
  `TYPE_APPLICATION_OVERLAY`. `voice/FloatingBubble` hosts a `ComposeView`, which needs its own lifecycle and
  saved-state owner. Remove every window you add.
- Singletons that outlive screens (`TaskManager`, `AuditLogger`) own a `SupervisorJob` scope on
  `Dispatchers.IO`; that is allowed here, `GlobalScope` is not. A new class like this takes its scope in the
  constructor, so a test can pass its own. Services cancel their scope in `onDestroy`.
- In suspend code, a `catch (e: Exception)` must rethrow `CancellationException` first. `GroqClient` and
  `GeminiClient` don't yet.
- Android 11+ hides other apps: a new intent or app lookup needs a `<queries>` entry in the manifest.

**New action types.** Change these together, in one commit:
- `data/model/ActionStep`: the constant and `KNOWN_ACTIONS`.
- `llm/PlannerPrompt.SYSTEM`: the exact JSON keys. The model can only use what it is told.
- `policy/PolicyEngine.classifyByAction`: its risk. Unknown actions fall back to HIGH.
- `agent/ActionExecutor.execute`: the branch, plus `NO_SERVICE_NEEDED` / `NO_SETTLE` if it doesn't use the screen.
- `agent/TaskManager.NO_AUTO_VERIFY` if a plan ending with it shouldn't get an automatic verify step.
- `skills/CloudSkillVetting`: what a downloaded skill may do with it.
- Never rename an existing action or JSON key: stored skills, `app_shortcuts.json` and cloud rows use them.
- `app_shortcuts.json` reaches every phone within a day of a merge, with no review on the phone. Bump its
  `version`, keep intents inside `isAllowedIntent`, put risky taps behind `confirm_send`, and keep
  `AppShortcutsTest` passing. Older app versions skip shortcuts that use actions they don't know.
- Skill steps are templates with `{slot}`s, never real contacts or messages (`SkillMatcher.templatize`).

**Build and data contracts.**
- Room: a new table or column means entity + DAO + a version bump in `AURADatabase` + an `AutoMigration`. Commit
  the generated JSON in `android/app/schemas/`; on a PR from this repo, CI commits it for you.
- `SkillPackEntity` stays `@Serializable`: the disk cache writes it as JSON.
- A new library may need `-keep` / `-dontwarn` lines in `android/app/proguard-rules.pro`. Run `assembleRelease`,
  and test a release APK on a phone, because reflection problems only show at run time.
- Native code is ARM only, so an x86 emulator can't run live tasks.
- Keep decision logic in plain Kotlin with no Android types (`AmountParser`, `SkillMatcher`, `TriggerMatcher`),
  so it runs in JVM unit tests. Android classes like `Uri` return null there, so pass them in, as
  `CloudSkillVetting.problem(skill, parseUri)` does.
- API keys are read only through `llm/ApiKeyStore`.

**Tests.**
- JUnit 4 and `kotlinx-coroutines-test` (`runTest`, `Dispatchers.setMain`). There is no mocking library: write a
  small fake that implements the real interface, like `FakeRules` in `policy/AppPermissionManagerTest`.
- `unitTests.isReturnDefaultValues = true` in `app/build.gradle.kts`, so `Log` calls are safe in tests, but
  `Uri.parse` returns null.
- Run one test class while working:
  `.\gradlew.bat testDebugUnitTest --tests "com.aura.policy.PolicyEngineTest"`
- Phone tests live in `docs/testing/phone-tests.md`. A change that affects the phone updates its row there.

## Checks
Run these from `android/` before handing off a change or refactor (`gradlew.bat` on Windows):
- Build debug APK: `./gradlew assembleDebug`
- Release build with R8 shrinking (CI runs it on every PR): `./gradlew assembleRelease`
- Unit tests: `./gradlew testDebugUnitTest`
- Android Lint (when touching layouts, resources, permissions or the manifest): `./gradlew lintDebug`
- No ktlint or detekt is configured.
- On Windows, use Android Studio's JDK and the SDK path in the gitignored `android/local.properties`
  (`sdk.dir=C\:\\Users\\<you>\\AppData\\Local\\Android\\Sdk`; Android Studio writes it when it opens the project).
  In PowerShell, from `android/`:

  ```powershell
  $env:JAVA_HOME = "C:\Program Files\Android\Android Studio\jbr"; .\gradlew.bat assembleDebug testDebugUnitTest
  ```
- Cloud sessions have no Android SDK. There, the "Android CI" run on the pushed branch is the check.

## Pushing and pull requests
- AI assistants follow `repo_rules.md` §6 here too: commit on a branch, never push, open a pull request or merge.
  This replaced the older `CLAUDE.md` workflow, where AI sessions pushed and merged, on 2026-11-21.
- After a commit, the assistant gives the user the commands to run, such as `git push -u origin <branch>`, and the
  link to open the pull request.
- Releases are the owner's: bump `versionCode` / `versionName`, add the CHANGELOG section, merge, then push the tag.
  `CLAUDE.md` has the steps.

## Other rules
- **One conversation, one task.** After about 15 turns, rewrite `HANDOFF.md` and suggest starting a new conversation.
- **Notes:** `HANDOFF.md` and `memory/` follow `repo_rules.md` §8. Both stay gitignored. The "Current status" and
  "Next steps" sections of `CLAUDE.md` are the shared project status: update them when a change moves the status.
- **Refactors stay scoped:** refactor one screen, ViewModel, or repository at a time. Keep behavior identical unless explicitly asked to change it.
- **No silent contract breaks:** never rename JSON/serialization fields (`@SerialName` in `ActionStep`, keys in
  `app_shortcuts.json`, Supabase columns), Room table/column names, navigation routes, DataStore/SharedPreferences
  keys, or exported Manifest components without explicit approval. A Room change needs a version bump and an
  `AutoMigration`.
- **Comment style:** existing code has KDoc and `// ────` banner comments. New and changed code follows
  `repo_rules.md` §7; don't restyle code you aren't otherwise changing.
