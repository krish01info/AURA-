## What is a Skill?

A **skill** is a recorded, reusable sequence of actions for a specific task in a specific app.

```
Skill: "whatsapp_send_message"
─────────────────────────────
App:      com.whatsapp
Intent:   messaging/send_message
Params:   { contact_name, message_text }
Risk:     HIGH
Steps:
  1. open_app(com.whatsapp)
  2. find_element(text: "{contact_name}")
  3. tap(first_match)
  4. find_element(hint: "Message...")
  5. type("{message_text}")
  6. confirm_send("Send to {contact_name}?")
```

Skills are **not written by developers**. They are auto-generated by AURA every time the LLM successfully plans and executes a new task.

## Skill Identity — No Duplicates by Design

Every skill has a **canonical ID** that is deterministically generated from its identity — not random. This makes it physically impossible for two different skills to exist for the same task.

### Canonical ID Formula

```kotlin
object SkillIdentity {

    fun generateCanonicalId(
        appPackage: String,
        intentCategory: String,  // e.g. "messaging"
        intentAction: String     // e.g. "send_message"
    ): String {
        val canonical = "${appPackage}::${intentCategory}::${intentAction}"
        return canonical.sha256().take(16)
    }
}

// Examples:
// com.whatsapp + messaging/send_message      → "a3f8c2d1e4b7a9c0"
// com.whatsapp + calling/make_call           → "b1d4e7f2c9a3b8d1"
// com.google.android.apps.nbu + pay/send     → "c7e2a4f8d1b3c9e5"

// Any user uploading "send WhatsApp message" 
// will ALWAYS get the SAME canonical ID
// → treated as an UPDATE, not a new skill
```

## Deduplication System

### The Four Duplicate Problems and Solutions

#### Problem 1 — Two Users Create the Same Skill

```
User A uploads: whatsapp_send_message with steps [A, B, C]
User B uploads: whatsapp_send_message with steps [A, B, D]

Without deduplication: 2 conflicting records in DB
With canonical ID:     same skill_id → second upload
                       triggers conflict resolver, not insert
```

**Solution**: Supabase `UNIQUE CONSTRAINT` on `(app_package, intent_category, intent_action)`

```sql
CREATE TABLE skill_packs (
    skill_id          TEXT PRIMARY KEY,
    app_package       TEXT NOT NULL,
    intent_category   TEXT NOT NULL,
    intent_action     TEXT NOT NULL,
    ...
    CONSTRAINT unique_skill UNIQUE (app_package, intent_category, intent_action)
);
```

---

#### Problem 2 — Multiple Keyword Triggers Match Same Goal

```
Goal: "send on whatsapp to Rahul"

Skill 1 triggers: ["whatsapp", "message", "text"]           → 1 match
Skill 2 triggers: ["whatsapp", "send on whatsapp", "wa"]    → 2 matches
Skill 3 triggers: ["whatsapp", "send", "message to"]        → 2 matches

Which one runs? → Scoring system decides (see below)
```

**Solution**: Multi-factor scoring system — the skill with the highest score wins.

---

#### Problem 3 — Old Version vs New Version Coexist

```
Before WhatsApp update: Skill v1 works (3,000 users have it cached)
After  WhatsApp update: Skill v1 breaks → User repairs → uploads v2

Problem: users with v1 cached locally still use broken skill
```

**Solution**: Supabase Realtime push notification when a skill version is bumped:

```kotlin
// Android client subscribes to skill version updates
supabase.realtime.channel("skill_updates")
    .on(PostgresAction.Update, table = "skill_packs") { change ->
        val updatedSkillId = change.record["skill_id"] as String
        val newVersion = change.record["version"] as Int
        val localSkill = localDao.getSkill(updatedSkillId)

        if (localSkill != null && newVersion > localSkill.version) {
            // Silently update local cache in background
            downloadAndCache(updatedSkillId)
        }
    }
    .subscribe()
```

---

#### Problem 4 — Same App, Different Phone Models

```
Samsung Galaxy: WhatsApp "New Chat" button ID = com.whatsapp:id/fab
Pixel 8:        WhatsApp "New Chat" button ID = com.whatsapp:id/new_conversation

Same task — different steps needed
```

**Solution**: Multi-strategy steps with device-scoped fallback (see Device-Scoped Skills section).

## Conflict Resolution

When a new skill upload conflicts with an existing one, this resolver decides the winner:

```kotlin
class SkillConflictResolver @Inject constructor(
    private val cloudApi: SupabaseSkillApi
) {
    suspend fun resolve(
        existing: CloudSkill,
        incoming: CloudSkill
    ): CloudSkill {

        // Rule 1: Higher version always wins
        if (incoming.version > existing.version) {
            return incoming.also { log("Conflict: newer version wins") }
        }

        // Rule 2: Same version — compare quality signals
        if (incoming.version == existing.version) {

            val incomingScore = qualityScore(incoming)
            val existingScore = qualityScore(existing)

            // Only switch if incoming is meaningfully better (5%+ improvement)
            return if (incomingScore > existingScore * 1.05f) {
                incoming.also { log("Conflict: higher quality wins") }
            } else {
                existing.also { log("Conflict: existing retained (stable)") }
            }
        }

        // Rule 3: Incoming is older version — always reject
        return existing.also { log("Conflict: incoming is older, rejected") }
    }

    private fun qualityScore(skill: CloudSkill): Float {
        // Weighted quality signal
        return (skill.successRate * 0.6f) +                    // 60% weight
               (minOf(skill.usageCount / 10_000f, 1f) * 0.3f) + // 30% weight
               (if (skill.isVerified) 0.1f else 0f)            // 10% weight
    }
}
```

```

      |
      v

      |

  YES    NO
   |      |
```

## Keyword Scoring — Which Skill Wins

When multiple skills match a user's goal, they are scored and ranked:

```kotlin
class SkillRouter @Inject constructor(
    private val skillRepo: SkillRepository
) {
    suspend fun findBestSkill(goal: String): SkillPackEntity? {
        val candidates = skillRepo.findAllMatching(extractKeywords(goal))

        if (candidates.isEmpty()) return null
        if (candidates.size == 1) return candidates.first()

        return candidates.maxByOrNull { scoreSkill(it, goal) }
    }

    private fun scoreSkill(skill: SkillPackEntity, goal: String): Float {
        var score = 0f
        val goalLower = goal.lowercase()

        // Factor 1: Keyword match count (max 50 pts)
        val keywords = skill.triggerKeywords.fromJson<List<String>>()
        val matchCount = keywords.count { goalLower.contains(it) }
        score += matchCount * 10f

        // Factor 2: Exact phrase match bonus (20 pts)
        if (keywords.any { goalLower == it }) score += 20f

        // Factor 3: Success rate — 0.0 to 1.0 (max 50 pts)
        score += skill.successRate * 50f

        // Factor 4: Usage count popularity (max 20 pts)
        score += minOf(skill.usageCount / 500f, 20f)

        // Factor 5: Community verified badge (15 pts)
        if (skill.isVerified) score += 15f

        // Factor 6: Device-specific match bonus (10 pts)
        if (skill.deviceModel == Build.MODEL) score += 10f

        // Factor 7: App version match (5 pts)
        if (skill.appVersion == getInstalledAppVersion(skill.appPackage)) score += 5f

        return score
    }
}
```

### Score Breakdown Example

```
Goal: "send whatsapp message to Rahul"

Skill A: "whatsapp_send_message" (community verified)
  Keyword matches:  2  × 10 = 20 pts
  Success rate:   0.94 × 50 = 47 pts
  Usage count:   8,000 / 500 = 16 pts
  Verified:              +15 pts
  ──────────────────────────────────
  TOTAL SCORE:           98 pts  ← WINNER

Skill B: "whatsapp_message_v2" (local, newer but unproven)
  Keyword matches:  3  × 10 = 30 pts
  Success rate:   1.00 × 50 = 50 pts
  Usage count:      5 / 500 =  0 pts
  Not verified:      +0 pts
  ──────────────────────────────────
  TOTAL SCORE:           80 pts
```

### Multi-Strategy Executor

```kotlin
class MultiStrategyExecutor @Inject constructor(
    private val accessibilityService: AURAAccessibilityService
) {
    suspend fun findElement(step: MultiStrategyStep): AccessibilityNodeInfo? {

        val strategies = step.strategies.sortedBy { strategy ->
            // Try device-specific strategy first
            if (strategy.device != null &&
                Build.MODEL.matches(strategy.device.toRegex())) 0 else 1
        }

        for (strategy in strategies) {
            val node = when (strategy.method) {
                "by_id"   -> accessibilityService.findById(strategy.value)
                "by_text" -> accessibilityService.findByText(strategy.value)
                "by_hint" -> accessibilityService.findByHint(strategy.value)
                else      -> null
            }
            if (node != null) return node  // first working strategy wins
        }

        return null  // all strategies failed → skill is stale
    }
}
```

## Self-Healing — Broken Skill Repair

When a skill starts failing (usually after an app update), AURA automatically repairs it:

```kotlin
class SkillUpdater @Inject constructor(
    private val localDao: SkillPackDao,
    private val cloudApi: SupabaseSkillApi,
    private val groqClient: GroqClient,
    private val anomalyDetector: SkillHealthMonitor
) {
    // Called after every skill execution
    suspend fun recordOutcome(skillId: String, success: Boolean) {
        localDao.updateSuccessRate(skillId, success)

        val skill = localDao.getSkill(skillId) ?: return
        val health = anomalyDetector.assess(skill)

        when (health) {
            SkillHealth.DEGRADED  -> checkForCloudUpdate(skillId)
            SkillHealth.BROKEN    -> triggerRepair(skill)
            SkillHealth.HEALTHY   -> Unit // no action needed
        }
    }

    private suspend fun checkForCloudUpdate(skillId: String) {
        val cloudSkill = cloudApi.getLatestVersion(skillId) ?: return
        val localSkill = localDao.getSkill(skillId) ?: return

        if (cloudSkill.version > localSkill.version) {
            localDao.upsert(cloudSkill.toEntity())  // silent background update
        }
    }

    private suspend fun triggerRepair(skill: SkillPackEntity) {
        // Mark stale so AURA falls back to LLM next run
        localDao.markStale(skill.skillId)

        // LLM will re-plan next time user runs this task
        // After success, SkillLearner saves the repaired steps as v+1
        cloudApi.flagForRepair(skill.skillId)
    }
}

class SkillHealthMonitor {
    fun assess(skill: SkillPackEntity): SkillHealth {
        return when {
            skill.successRate >= 0.85f -> SkillHealth.HEALTHY
            skill.successRate >= 0.60f -> SkillHealth.DEGRADED   // investigate
            else                       -> SkillHealth.BROKEN      // repair now
        }
    }
}

enum class SkillHealth { HEALTHY, DEGRADED, BROKEN }
```

### Repair Flow

```
Skill successRate drops below 0.60
          |
          v
Mark isStale = true in local DB
          |
          v
Next user command → skill is stale → skip it
          |
          v
Fall back to Groq LLM → plans + executes → SUCCESS
          |
          v
SkillLearner saves new steps as version = old_version + 1
          |
          v
Upload to Supabase cloud
          |
          v
Supabase Realtime notifies all users with old version
          |
          v
All users silently update their local cache
```

## Key Design Rules

1. **One canonical skill per intent** — `UNIQUE(app_package, intent_category, intent_action)` enforced at DB level
2. **Higher version always wins** — conflict resolution always respects version numbers
3. **Stale > retry** — never delete a skill, mark it stale and let LLM repair it
4. **Local first** — always check Room DB before any network call
5. **Score, don't guess** — when multiple skills match, always use scoring, never random
6. **Device-scope, don't duplicate** — use multi-strategy steps instead of separate skills per device
7. **Community verifies, usage validates** — verified badge requires real usage data, not just votes
8. **Silent updates** — skill updates happen in background, never interrupt user
